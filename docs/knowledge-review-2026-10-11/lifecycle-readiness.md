# 知识生命周期：发布前收敛与重构范围

状态：2026-10-11 的代码审查与工作顺序。仍在开发期，本文不声明内测或正式发布通过。

## 优先级和现有边界

本轮优先验证知识从生成、整理、发布、维护到再次使用的生命周期。remote-dev 沿用已有实现与验证，只检查知识交付所依赖的版本组合和更新交接，不把成熟远端能力的全量重验作为本轮前置条件。Kimi、Claude Code 和其他可选组件单独报告支持范围，不用它们的移植扩大当前 Codex 知识任务。

按[九条设计原则](../design-principles.md)和[架构](../architecture.md)，现有三项边界值得保留：完整脱敏 Markdown 块拥有正文事实，SQLite 拥有进度、授权关联与执行回执，ReMe 是可重建的检索派生物。原生身份、解析和模型调用属于适配器。知识核心的重构不需要更换这些权威边界，也不需要另造在线服务或统一 Harness。

在所有仓库达到发布标准并声明正常版本前，可以反复破坏性调整格式；没有“一次重建”的额度。已有有效材料和执行证据仍应尽量复用，已知错误不能伪装成空库。正式发布后，兼容升级保留原始材料、进度、模型调用结果与未知写入身份；不兼容升级须明确迁移，否则保留旧运行时并拒绝候选。

## 可独立收敛的实现风险

审查起点是知识核心主线 `c23e38b0f06bd2cc433b927a5a37f4b762cb6823`，生产代码与已验收候选 `7c99fbb387304c0e4b26ca85c1839bed8b7534be` 相同。下面的复现使用隔离合成状态，不调用付费模型，不创建外部投稿。

| 风险 | 代码依据和已复现行为 | 收敛方式 |
| --- | --- | --- |
| 授权恢复后仍无法投稿 | `Engine` 在停用时置位共享取消标记，只有先前授权版本非空才清除；停用启动后启用、启用后停用再启用均阻塞新投稿 | 新授权获得新的操作取消标记；旧标记永久保持取消，旧未发送材料不回填 |
| 后台观察授权变化晚于新材料入队 | 旧 `_cancel_unsent` 取消全部 pending 批次和未发送反馈，会连带取消当前新授权下的工作 | 根据现有授权版本保留新批次、反馈和正在运行的新授权整理操作，只取消旧工作 |
| 停用发生在首次启用轮询之前 | 整理 worker 已按启用状态接收工作，但 outbox 缓存授权仍为 `None`；明确停用与缓存相同导致漏取消 | 明确撤销检查实际操作的取消状态，不要求 outbox 先观察到启用；首次停用取消已接收工作，持续停用不重复写入 |
| 对账失败覆盖原发布事实 | 只读对账抛出 `OSError` 时，把原 `unknown` 回执的原因改成对账失败；相同状态不产生新的 Agent 错误交付 | 对账失败作为独立阶段诊断，不改原外部写入事实；恢复后再次失败可以再次交付 |
| 已确认的远端结果被本地记账失败遮蔽 | 对账返回精确远端结果后，SQLite 记账失败未在异常中保留已返回结果 | 投稿和对账共用回执记录边界；异常保留返回结果和记录失败阶段，不据此重新写入 |
| 冻结材料加载故障定位不足 | 冻结 manifest 丢失时虽标为 unavailable，Agent 只获得泛化回执阶段，实际材料加载阶段未交付 | 投稿开始前报告 payload 阶段及原诊断引用；保留未开始写入事实，不能发送空材料 |

这些修复不改变公开正文格式，不新增模型步骤、用户参数或日常维护命令。测试依据状态和实际工作次数，不以某个任意秒数作为产品性能或成功门槛。它们应成为后续重构的回归约束，不能用测试数量宣称完整生命周期通过。

修复候选见[知识 PR #62](https://github.com/mindie-agent/knowledge/pull/62)。提交 `cc9859f99f125bee00136a3e0aa14f82b65a0278` 的 Ubuntu/macOS CI 均为 888 passed / 9 skipped，Windows 为 867 passed / 30 skipped，package CI 成功。随后补查的首次停用两个参数场景在该提交均失败；修复后的提交 `448b359575b57b233726bf7d0db53d28fafa0968` 上，授权、配置、故障恢复、整理生命周期和错误交付的受影响集合为 100 passed。最后提交的全量 CI 需另行核对，不能借用前一提交结果。

[真实后台线程复验](lifecycle-local-evidence.json)使用正常 editable 开发安装和完整声明依赖，分别验证“停用启动后启用”和“启用→停用→再启用”：新授权已观察、新操作未取消、旧标记仍取消；正文通知、模型尝试和 outbox 均为零，未调用模型或写入外部系统。该复验不冒充 native Hook 验收，测试 watchdog 不是产品期限。本机插件尚未切换至此候选。

## 发布前需要的局部重构

需要进一步整理生命周期编排。依据是已经复现的授权与操作取消耦合，以及投稿、对账的同一回执语义曾分散实现；单凭文件很大不构成重构理由。

`Engine` 应负责调度、当前操作所有权和授权交接。正文提交、索引执行结果、发布意图/远端证据、公共 feed 切换各自拥有明确的领域操作和事务边界。可以逐步从 `Store` 中分离领域操作，但继续复用同一个权威状态库和事务，避免用拆文件制造第二套状态权威。

先写清以下转换的业务事实、允许动作和恢复来源，再移动实现。并行存在的多个增量、模型尝试和投稿，不应被压成一个全局阶段字段。

| 边界 | 必须成立的事实 | 恢复或下一步 |
| --- | --- | --- |
| 授权与准入 | 明确区分未配置、停用、授权损坏和当前授权；每个增量绑定原生身份、范围、授权版本 | 损坏时停放；撤销时旧未发送材料不回填；当前新材料独立前进 |
| 正文与进度 | 正文块与对应游标一起提交，重复 Stop 不重复正文 | 从已提交游标继续；提交后的推广或清理失败另报，不重新读旧正文 |
| 索引与模型结果 | prepare、已开始调用、已返回结果和已本地应用可区分 | 已返回结果只重做本地应用；已知失败或结果未知的模型输入不自动重放；后续增量独立保存和整理，仍有旧块未完成索引时整包明确未就绪 |
| 投稿与远端证据 | 冻结文件、原写入意图、预期精确 head 和当前远端观测可区分 | 结果未知只核对原操作；已确认的结果不能因记账或清理失败变成未执行 |
| 公共版本与维护 | 当前公共成员、维护者修正、完整撤下、旧引用状态和未发布新块可区分 | 同步当前 feed；后续增量保留公共修正和撤下决定，不能把它们覆盖回生产者旧版本 |

重构完成的标准是：每个恢复入口能从已持久化事实确定允许动作，不需要猜另一 worker 的全局标记；旧失败不阻塞其他正常任务，同任务后续增量可以继续保存和整理；尚未完成的必要索引不会被隐藏为整包就绪，错误与明确重试入口到达 Agent；正文不会由导航模型改写。避免扩大为语义去重、自动真实性认证或通用工作流平台。

另一个耦合在 Codex `candidate_validate.validate`：公开合同的 trusted validator revision 必须等于安装的知识 runtime revision。因此即使只修复本地队列、公开格式和校验行为均未变化，简单更新 runtime pin 也不能通过现有候选校验；它会要求公开合同、适配器和外部 Bot 的组合联动。不能把一个 requirements 更新当成已交付修复。

这已通过[真实候选校验实验](runtime-validator-coupling-evidence.json)复现：隔离 Codex 候选只有知识依赖从已验收版本更新至 `cc9859f`，正常非 editable 安装的实际 Git pins 与候选声明匹配；候选自带校验器读取现有公开合同后返回 `publication_contract / validator_mismatch`。remote-dev pin 不变，没有切换本机插件、调用模型或外部写入。它是被拒绝的候选实验，不是已交付的新产品组合。

发布前应明确区分运行时可执行代码身份、公共材料格式兼容性和 trusted-base 审核代码身份，再决定何种变更需要共同更新。具体边界调整必须保留各自可信精确 pin、声明摘要和真实互操作验证，不能直接删除等值检查后宣称兼容。此次没有放宽校验或改变公共合同。

## 后续工作及对应验收

| 顺序 | 工作 | 能解决什么 | 通过依据 |
| --- | --- | --- | --- |
| 1 | 合入上述局部修复及回归约束 | 先从核心实现移除确定的正常路径故障，避免在已知错误上继续验收 | 精确 core 提交、受影响测试及最终提交 CI；尚未更新的插件不能借用此结果 |
| 2 | 按领域整理生命周期编排、事务边界与交付合同，再交付 Codex 组合 | 降低恢复路径相互干扰，以及普通 runtime 修复要求全生态同步的返工成本 | 上述转换在正常、重启和交错条件下保持同一业务语义；可信代码身份与格式兼容性各自可核对；实际安装和宿主已加载定义分别报告 |
| 3 | 跑通维护后的完整生命周期 | 检验知识持续变化而非只验证首次投稿 | 正常事件审核/合入、维护者修正、版本反馈、完整撤下、生产者后续增量和独立消费者同步读取，精确核对正文和引用 |
| 4 | 收敛现有 Bot 的授权语境冲突 | 首轮和增量虽已实际合入，两次仍需人工响应，不能算无人值守通过 | 正常事件在既有纯内容授权下完成；维护检查、开发 PR 与未知外部写入仍遵守各自边界，不通过扩大 Always allow 权限绕开 |
| 5 | 验证使用收益、增长成本和正式升级 | 决定是否达到可发布标准 | 自然业务可选择使用知识的实际收益；新增块、warm query、idle、重启的工作量与资源增长；真正旧正常版本的状态升级与拒绝/保留行为 |

步骤 3、4 属于跨系统真实验收，不能由本地 mock 代替。收益验证不能增加必查、必写或强制反馈；资源负载不是运行时的材料数量或执行时长上限。现有正式升级测试使用模拟 release 声明，是回归证据，不能冒充已发布版本间的升级验收。

10 月 11 日原生首轮、增量和独立消费者的已有事实见[Bot 验收记录](bot-contract-acceptance.md)。真实修正、撤下、无人值守合入和普通业务复用收益仍需补证；已有成熟组件的证据继续复用。修复合入、局部重构完成和知识系统达到发布标准是三个独立结论。
